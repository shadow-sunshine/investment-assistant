## 2. 发现并修复的问题

### P0/P1：画像上下文之前没有进入真实受控调用

原实现生成了 `assembled`，但调用适配器没有收到它。现在通过 `conversation_memory` 参数传入，并在 API 的对话适配层显式保留；回答组织会显示研究偏好提示，但偏好不改变财务事实证据。

### P0/P1：会话确认可能应用另一会话的待确认候选

原实现按用户列出 pending 候选，没有严格绑定当前 `conversation_id`。现在确认、拒绝、全部删除和 API staging 都校验会话归属；待确认候选替换、版本不符、过期和跨会话重放均拒绝。

### P0/P1：确认与画像写入不是同一事务

现在候选版本检查、旧值检查、画像写入、候选解决、撤销派生状态在 SQLite 事务内完成，避免并发确认产生双写或旧值覆盖。

### P1：用户输入异常时可能显示无回复或泄露内部异常

现在异常会持久化为可理解的中文失败回复，内部错误类型只保留在受控元数据；界面提供重试，不显示地址、凭证或本地路径。

### P1：重复 request_id 在工具调用前没有抢占

现在先在事务中 claim 用户请求；同一身份、同一 request_id 不能跨会话复用，也不会并发执行两次。迟到回答必须写回原会话；原会话已删除时不复活。

### P1：短期状态存在被旧 dispatch 结果覆盖的风险

现在在编排层保留并合并当前结构化状态，补充市场/公司/年份/指标状态；模式切换保留消息但清除不适用证据范围。

### P1：刷新后 URL 没有恢复会话

现在 URL 只保存会话 ID，服务端重新做权限校验后恢复会话消息和状态；不保存 token 或画像正文。新建、切换、发送后会更新当前会话 ID。

### P1：删除画像后旧状态和摘要可能复活偏好

现在画像撤销会同步清理各会话的临时偏好/硬约束、待确认候选和摘要；历史消息仍可展示，但后续上下文不会使用已撤销画像。

### P2：上下文窗口行为表达不准确

保留 32,000 token 作为应用层估算提醒，不宣称模型额度；近期历史受轮数和预算双重限制。超过预算时不静默丢掉有效约束，而是返回澄清结果。

### P2：MCP/官方回答适配器接线不完整

对话链路现在复用官方公司问答和官方文档待核验检索；MCP 仍显式标为候选并与官方证据分区。报告追问通过既有发布/访问门禁，不直接加载未发布报告。

## 3. 当前实现范围

- SQLite：`data/conversation_memory.sqlite3`，开发运行文件已加入 `.gitignore`，支持 WAL/事务。
- 新增模块：
  - `investment_assistant/conversation_store.py`
  - `investment_assistant/conversation_memory.py`
  - `investment_assistant/user_profile.py`
- API：会话创建、列表、读取消息、重命名、模式切换、删除、发送轮次；用户画像读取、候选 staging、确认/拒绝、单项/全部删除。
- UI：左侧最近会话、新对话、切换、重命名、删除确认、模式切换、研究偏好入口；发送时显示真实处理中状态，失败显示中文重试信息。
- 画像：只保存用户明确陈述并经确认的研究偏好；敏感内容不进入画像、不发送到工具；画像不作为财务事实证据。
- 短期状态：本公司、市场、年度、指标、待补槽位、临时偏好、硬约束和受控摘要。
