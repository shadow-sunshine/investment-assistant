# 报告审计链设计：让系统回答 7 个业务问题

> 目标项目：`Investment_Assistant`
> 版本：v1.1 · 2026-09-22
> 状态：**Phase A 已实现并验收**（见 §10）；Phase B–E 待做

---

## 1. 背景与目标

当前系统能生成"可追溯的投研报告"，但**不能回答关于报告本身的业务问题**。需要让它能回答：

1. 这份报告是谁发起的？
2. 当前生成到了哪一步？
3. 哪个数据源失败了？
4. 为什么用了规则版？
5. 哪条结论由哪些证据支持？
6. 谁审核过这份报告？
7. 这次模型或 Prompt 改动有没有导致质量下降？

---

## 2. 现状盘点（基于实际代码）

| # | 问题 | 现状 | 依据 |
|---|---|---|---|
| 1 | 谁发起的 | ❌ 缺 | `api.py:22-25` `GenerateReportRequest` 只有 ticker/topic/horizon |
| 2 | 到哪一步 | ❌ 缺 | `api.py:111-126` `POST /api/reports` 同步阻塞，执行完才返回 |
| 3 | 哪个源失败 | △ 半 | 散落 5 处：`workflow.py:77`(market)、`workflow.py:105-106`(financial)、`:147`(news)、`:145`(local)、`:70`(retrieval_status) |
| 4 | 为什么规则版 | ✅ 有 | `workflow.py:118-119`（用户指定）、`:230-232`（校验失败降级）；`api.py:62-66` `_mode_info` |

**结论：1 个能答，3 个半答，3 个答不了。**

## 3. 本质诊断

系统现在产出的是 **「数据快照 + 报告文本 + 散落的状态字段」**。

它缺的是 **责任链（Accountability Chain）**：

```
谁发起 → 何时 → 当前到哪步 → 每步是否成功 → 依据哪些数据/证据
   → 为何降级 → 谁审核批准 → 与上次相比质量如何
```

`audit_json()`（`workflow.py:270-271`）导出的是 `ResearchState` 的**状态切片**，不是**可追问的流程**。

---

## 4. 核心设计：`ReportJob` 实体

把"报告"从**函数的返回值**升级为**有生命周期的任务**。

```python
class SourceHealth(TypedDict):
    name: str          # market / financial / news / local_rag
    status: str        # ok | degraded | failed | skipped
    reason: str | None # 失败或降级原因
    duration_ms: int
    fetched_at: str | None

class StepRecord(TypedDict):
    node: str          # collect_real_data / retrieve_evidence / ...
    status: str        # pending | running | succeeded | failed | skipped
    started_at: str
    ended_at: str | None
    summary: str       # 该步产出摘要，如 "sources=4" / "mode=rule"

class ClaimEvidence(TypedDict):
    claim_id: str            # C1, C2, ...
    text: str                # 结论文本
    evidence_refs: list[str] # ["S1", "S2"]
    support_status: str      # supported | partial | unsupported   ← 治 KI-001

class ReviewRecord(TypedDict):
    reviewer: str
    reviewed_at: str
    decision: str            # approved | rejected | changes_requested
    comment: str

class FallbackInfo(TypedDict):
    mode: str                # llm | rule
    category: str            # user_specified | safety_rejected | llm_error | no_data
    reason: str
    detail: dict

class ReportJob(TypedDict):
    id: str
    requested_by: str                      # ← 问题 1
    status: str                            # pending|running|awaiting_review|succeeded|failed
    current_step: str | None               # ← 问题 2
    created_at: str
    finished_at: str | None
    steps: list[StepRecord]                # ← 问题 2
    source_health: list[SourceHealth]      # ← 问题 3
    fallback: FallbackInfo                 # ← 问题 4
    claims: list[ClaimEvidence]            # ← 问题 5
    review: ReviewRecord | None            # ← 问题 6
    versions: dict                         # {model, prompt_version, code_version}
    evaluation: dict                       # 含 baseline 对比      ← 问题 7
```

**这个实体本身就是"能回答 7 个问题"的载体。**

## 5. 每个问题的解法映射

| # | 问题 | 由什么回答 | 新增/改动 |
|---|---|---|---|
| 1 | 谁发起的 | `job.requested_by` | 入口增加调用方标识（MVP 用参数/header，将来接用户体系） |
| 2 | 到哪一步 | `job.status` + `current_step` + `steps[]` | **异步执行**：`POST /api/jobs` 立即返回 id，后台跑 |
| 3 | 哪个源失败 | `job.source_health[]` | 每个 fetch 包一层 recorder，记录 status/reason/耗时 |
| 4 | 为什么规则版 | `job.fallback.category` | 把现有 `llm_result.reason` 从**自由文本**升级为**枚举分类** |
| 5 | 结论↔证据 | `job.claims[]` | 叙述按 claim 切分，每条挂 `evidence_refs` + 支持性判定 |
| 6 | 谁审核 | `job.review` | 新增审核端点 + 状态流转 `awaiting_review` |
| 7 | 质量是否下降 | `job.versions` + `evaluation.baseline` | 版本标识 + 评估结果与基线对比 + 门禁判定 |

## 6. 实施层次（分 5 期，可独立交付）

### Phase A · 任务化（答问题 1、2）
- [ ] `ReportJob` 数据结构 + 持久化（JSON 文件即可，与现有 `data/reports/` 一致）
- [ ] `POST /api/jobs` 异步执行，立即返回 `job_id`
- [ ] `GET /api/jobs/{id}` 返回状态 + current_step + steps
- [ ] `GET /api/jobs` 列表
- [ ] 入口加 `requested_by`

### Phase B · 源健康 + 降级结构化（答问题 3、4）
- [ ] `SourceRecorder` 包裹 market/financial/news/local_rag 四个数据源
- [ ] `fallback.category` 枚举化（复用现有 `llm_result.reason`）

### Phase C · Claim-Evidence 追踪（答问题 5，同时治 KI-001）
- [ ] **后处理方式**（关键约束见 §7）：从已生成报告的第 4 节叙述中解析出 claim
- [ ] 每条 claim 关联其携带的 `[Sx]` 引用
- [ ] `support_status` 判定（supported / partial / unsupported）
- [ ] 对 `unsupported` 的 claim 生成告警

### Phase D · 审核流（答问题 6）
- [ ] `POST /api/jobs/{id}/review` 提交审核结论
- [ ] 状态机加入 `awaiting_review`
- [ ] 未审核的报告标记为"未审核"，不可直接对外

### Phase E · 版本与门禁（答问题 7）
- [ ] 记录 `model` / `prompt_version` / `code_version`
- [ ] 评估结果与上一基线对比，输出 `delta`
- [ ] 质量下降超阈值 → 门禁拦截（告警或阻断）

## 7. 关键约束：不能破坏冻结边界

项目当前对 **检索 / LLM / 安全** 三块是 **frozen** 状态（README 明确"不再改 prompt/检索/重排"）。

因此 **Phase C 有一个重要设计选择**：

| 方案 | 做法 | 风险 |
|---|---|---|
| ❌ 改 prompt | 让 LLM 直接输出结构化 claim | **触碰冻结边界**，可能破坏 5/5 验收 |
| ✅ **后处理**（推荐） | 报告生成后，从第 4 节叙述中**解析**出 claim 与引用 | 不动 prompt，只加一层解析与校验 |

**推荐后处理方案**：因为 LLM 输出的叙述里**本来就带 `[Sx]` 标记**，后处理只需把它切成句子级 claim 并抽出引用，再判定支持性。

其余 Phase（A/B/D/E）都是**新增层**，不改动核心工作流，与冻结边界不冲突。

---

## 8. 风险与注意

| 风险 | 说明 | 对策 |
|---|---|---|
| 异步引入复杂度 | 从同步变异步，需要任务存储与并发控制 | MVP 用文件 + 后台线程即可，别上 Celery |
| `steps[]` 与 LangGraph 耦合 | 步骤记录要挂到节点上 | 用 LangGraph 的回调/事件机制，别改节点内部逻辑 |
| Claim 切分不准 | 中文叙述切句可能有歧义 | 先做粗粒度（段/句），标注 `support_status=partial` 容错 |
| 门禁阈值难定 | 什么算"质量下降" | 先只记录 `delta` 不拦截，积累数据后再定阈值 |
| `requested_by` 身份来源 | 现在没有用户体系 | MVP 从请求参数取，明确标注"临时方案" |

### 10.2 关键实现决策

1. **不碰冻结边界，也不碰 `workflow.py`。**
   进度通过在编译图外层订阅 `stream_mode=["updates", "values"]` 采集；最终状态取自 `values` 的最后一个快照（框架产出），**不做手工合并**。
   该假设由 `test_streamed_final_state_equals_invoke_on_real_graph` 用**真实图**钉死（节点替换为离线桩）：`streamed_final == invoked` 且节点顺序与 `WORKFLOW_STEPS` 一致。

2. **异步入口不做网络校验。**
   `POST /api/report-jobs` 只走 `_normalize_request`（纯函数），把 ticker 存在性检查留给作业自身——这样提交延迟与网络无关。

3. **幂等。** 相同 `(ticker, topic, horizon)` 在跑时复用既有 `job_id`，返回 409 + 既有 id。

4. **取消是协作式的**，在**节点边界**生效：在途节点跑完，其后节点标 `skipped`（不是 `failed`——它没有出错）。

5. **陈旧任务回收。** `recover_stale_jobs()` 把上次进程遗留的 queued/running 标为 failed，避免永远卡在 running。

6. **`JobExecutor` 抽象**已就位，将来换 Celery/RQ 只需实现该接口，API 层零改动。
