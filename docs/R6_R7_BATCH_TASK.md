## 1. R6：单机团队身份边界与审核发布

**身份/租户。** 做服务器验证的最小身份适配（例如本地环境变量提供的高熵 token→actor/tenant/roles 映射，服务端常量时间比较；不把明文 token 写日志或落盘）。明确这是单服务、本地演示级真实鉴权，不等于企业 OIDC/SSO 或生产密钥管理。无配置/无效/过期 token、伪造 requested_by、跨 tenant 的相同 report_id/job_id、越权读/写均拒绝且不得返回资源存在性细节。认证、授权与审计分别成层，不靠隐藏 UI。

**资源归属及 API 全覆盖。** 给新报告、任务、问答、交付状态、审核记录、R7 资源绑定不可由请求者自行覆盖的 tenant_id/actor_id；老报告无可信归属时隔离为迁移待审，绝不默认公有。建立路由矩阵并统一服务端依赖：`POST/GET /api/reports`、单报告、delivery、`POST /api/answers`、job 创建/列表/单条/报告/取消、审批/发布端点及任何原始文件/下载入口。后台执行任务继承创建时的不可伪造归属；列表严格过滤，404/403 策略一致，避免枚举。source-health 若含租户数据也隔离。

**人工审核与发布。** 增加 `review_status`、`publish_status`，仅指定 reviewer 可确认逐条 claim 与报告覆盖范围，publisher 或独立角色按策略发布；创建人不能自己审核/发布（职责分离）。审核基于当前报告 Markdown + JSON 的字节 SHA、资料 SHA、claim 集版本、tenant、report_id；任何这些字节变化后旧审核失效。无完整 claim 覆盖证据或结构门禁不通过时不能发布；不能用单条良好 fixture 代替整份报告覆盖。无法自动证明语义支持时必须明确由人工逐条审阅并记录 reviewer、时间、决定、理由和证据版本，不把系统校验误称为自动零幻觉。拒绝、撤回、重审和并发重复动作须确定性处理；发布前和每次读取前重新校验当前版本、授权和门禁。

**审计留痕。** 持久化记录 actor、tenant、action、target、result、timestamp、版本与错误码；原子写入/并发安全，敏感 token 和未发布正文不得写入。日志可追溯但不声称外部不可篡改；配置不全时 fail-closed。

**前端。** 在既有 Streamlit 风格上加入明确登录/当前身份与租户、待审/已拒/发布状态、可解释的 409/422 拒答、审核操作入口；未发布正文不可见且不可通过刷新/直连/API/缓存/下载获得。不得把共享进程中的单一全局 token 冒充多用户隔离。宽屏与窄屏检查，并真实走主交互；不能只凭单测称 UI 完成。

**R6 离线门禁。** 无认证、伪造 requested_by、跨租户 report/job/answer/list/delivery/取消/下载、审核人自审、并发双发、旧 SHA/原件修改后旧审批重放、结构证据不合格仍请求发布、未发布 UI 缓存泄漏，均应被拒绝。成功链：actor 创建→另一 reviewer 对完整 claim/正文人工审核→合规 publisher 发布→授权读取→撤回后读取拒绝。单元/API 与 UI 测试结果分开记录。

## 2. R7：版本监控与受控研究记忆

在 R6 边界之上实现最小单机版本监测：按 tenant/actor 授权的 watchlist，对白名单本地资料 manifest 和已发布报告的 SHA/版本做显式触发检查（手动或受控任务），标出新增/修改/缺失；记录上次检查时间、错误和可复跑 diff。SHA 漂移或数据源不可用不得补成肯定的“结论变化”，应返回 `needs_review`/`source_unavailable`。不得把 R0/R3 离线实验写成生产监控效果。

研究记忆仅保存可撤销、有限期、版本绑定的摘要/用户偏好；每条有 tenant、owner、report_id、证据/审核/发布时间版本、创建与到期时间。只引用仍已发布且当前有效的报告；跨租户、过期、撤回、报告/证据版本变更时拒绝注入问答，并可显式删除。结论对比只能在同 ticker 且两个可读已发布版本之间运行，给事实差异、来源/期间/单位及无法比较原因，不自动给买卖建议。不要构造开放式无限记忆或未授权联网搜索。

**R7 离线门禁。** watchlist/记忆 CRUD 授权、跨租户隔离、TTL 过期、撤回/版本漂移失效、并发重复检查幂等、两份报告的期间/单位不一致拒绝肯定比较、资料缺失不生成伪变化；成功链从白名单材料版本变化到待审提醒到人工处理，均给确定性 fixture。
